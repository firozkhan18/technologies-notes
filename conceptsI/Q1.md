# Complete Real-Time Java & Spring Boot Interview Checklist

I'll organize the questions into interview-preparation topics, with questions only and no answers. You can use this as a revision tracker.

## 1. Microservices architecture

- [ ]Q1. Product Service is working, but Inventory Service is down. What should happen when a customer places an order?
This is a very common Microservices real-time scenario interview question. It tests fault tolerance, service communication, transaction management, and data consistency.

## Scenario

Suppose you have an e-commerce application with these microservices:

- Product Service: Provides product details and prices.
- Inventory Service: Checks available stock.
- Order Service: Creates customer orders.
- Payment Service: Processes payments.

A customer tries to purchase a product, but Inventory Service is DOWN.

Normal order flow

Customer

Order Service

Product Service — Available

Inventory Service — DOWN

Stock availability cannot be confirmed.

## 1. What should happen?

The safest approach is:

1. Customer sends an order request.
2. Order Service validates product details using Product Service.
3. Order Service calls Inventory Service to reserve stock.
4. Inventory Service is unavailable.
5. Order Service should NOT confirm the order.
6. Return a meaningful response to the customer.

Example response:

json

```json
{
  "orderId": null,
  "status": "ORDER_PENDING",
  "message": "Unable to verify inventory. Please try again later."
}
```

The exact status depends on your business workflow. You could also reject the request immediately with HTTP 503 if you do not persist pending orders.

Important: Never assume stock is available just because Product Service is working.

## 2. How do we handle this technically?

Use the following resilience patterns.

### A. Circuit Breaker

Use Resilience4j Circuit Breaker.

It has three states:

- CLOSED: Requests are allowed.
- OPEN: Requests are blocked because failures exceeded the threshold.
- HALF\_OPEN: A limited number of requests are tested to check recovery.

Finnally I Decide to Handle Timeout and Connection Pool Exhaustion in Biller-Service Using Resilience4J Circuit Breaker | by M. Khoironi | Medium

[medium.com](<https://medium.com/%40onimaksut01/finnally-i-decide-to-handle-timeout-and-connection-pool-exhaustion-in-biller-service-using-9442bfed9b85?utm_source=chatgpt.com>)

Example Spring Boot implementation:

java

```java
@Service
public class OrderService {

    private final InventoryClient inventoryClient;

    public OrderService(InventoryClient inventoryClient) {
        this.inventoryClient = inventoryClient;
    }

    @CircuitBreaker(
        name = "inventoryService",
        fallbackMethod = "inventoryFallback"
    )
    public String placeOrder(Long productId, int quantity) {

        boolean available =
            inventoryClient.checkStock(productId, quantity);

        if (!available) {
            throw new RuntimeException("Out of stock");
        }

        return "Order placed successfully";
    }

    public String inventoryFallback(
            Long productId,
            int quantity,
            Throwable ex) {

        return "Inventory service unavailable. Try again later.";
    }
}
```

In production, distinguish between an actual out-of-stock response and a service failure. A fallback must not turn a service failure into a successful order.

### B. Timeout

Configure a connection timeout and response timeout.

For example:

- Connection timeout: 1 second.
- Response timeout: 2 seconds.

This prevents Order Service from waiting indefinitely.

### C. Retry

Retry temporary failures with exponential backoff.

For example:

- First attempt: immediately.
- Second attempt: after 1 second.
- Third attempt: after 2 seconds.

Do not retry indefinitely. Also, retry only when appropriate and use idempotency protection.

### D. Saga Pattern

If your workflow includes payment and multiple services, use the Saga pattern.

Example:

1. Create Order
   Order status = PENDING
2. Reserve Inventory
   Inventory Service unavailable.
3. Keep Order Pending
   Do not proceed with payment.
4. Retry inventory reservation
   When Inventory Service recovers.
5. Complete Order
   Reserve stock, process payment and confirm order.

If payment was already processed before inventory reservation failed, use a compensating transaction to refund the payment.

## 3. What if the interviewer asks: Can we use Kafka?

Yes\!

Instead of synchronous communication, you can use event-driven communication.

Example:

1. Order Service publishes `OrderCreated`.
2. Inventory Service consumes the event.
3. Inventory Service checks and reserves stock.
4. Inventory Service publishes `InventoryReserved` or `InventoryRejected`.
5. Order Service updates the order status.

This allows services to work independently, but it introduces eventual consistency.

You must also handle duplicate events, retries, message ordering and failed messages.

## 4. Interview-ready answer

You can explain it like this:

> If Inventory Service is down while Product Service is working, I will not confirm the order because stock availability cannot be guaranteed.
>
> I will implement a Circuit Breaker using Resilience4j to prevent repeated calls to the unavailable service. I will configure appropriate timeouts and limited retries with exponential backoff.
>
> Depending on business requirements, I can either reject the order with HTTP 503 or create a PENDING order and process it asynchronously using Kafka.
>
> Once Inventory Service recovers, we can retry the inventory reservation. If payment has already happened, we need a Saga compensating transaction to refund it.
>
> I will also ensure idempotency to prevent duplicate orders or payments.

# 1. What happens if Inventory Service recovers but the same order event is consumed twice?

## Scenario

Suppose a customer places an order for one mobile phone.

1. Order Service publishes `OrderCreated` to Kafka.
2. Inventory Service consumes the event.
3. Inventory Service reserves one mobile phone.
4. Inventory Service crashes before committing the Kafka offset.
5. Inventory Service restarts.
6. Kafka delivers the same event again.

Now Inventory Service receives the same order twice.

Problem Without protection, inventory could be reduced twice.

## Solution: Idempotency

Idempotency means executing the same operation multiple times produces the same final result as executing it once.

Use a unique `orderId` or `eventId` to identify each operation.

Database table:

sql

```sql
CREATE TABLE processed_events (
    event_id VARCHAR(100) PRIMARY KEY,
    processed_at TIMESTAMP
);
```

Spring Boot example:

java

```java
@Service
public class InventoryConsumer {

    @Transactional
    public void consume(OrderCreatedEvent event) {

        if (processedEventRepository
                .existsById(event.getEventId())) {
            return;
        }

        inventoryRepository.reserveStock(
            event.getProductId(),
            event.getQuantity()
        );

        processedEventRepository.save(
            new ProcessedEvent(event.getEventId())
        );
    }
}
```

The inventory update and processed-event record must be committed in the same database transaction.

For stronger concurrency safety, enforce the unique event ID constraint in the database and handle duplicate-key conflicts.

Interview answer:

> Kafka generally provides at-least-once delivery in common consumer configurations. Therefore, duplicate events are possible. I implement idempotent consumers using unique event IDs and a processed-events table. I save the event record and update inventory in the same database transaction so that duplicate delivery does not reserve stock twice.

# 2. What happens if stock is reserved but Payment Service goes down?

## Scenario

A customer orders a laptop for ₹50,000.

- Order Service creates an order.
- Inventory Service reserves the laptop.
- Payment Service is unavailable.

The stock is reserved, but payment hasn't completed.

1. Order Created
   Success
2. Stock Reserved
   Success
3. Payment Processing
   Service unavailable
4. Release Inventory
   Compensating transaction
5. Cancel Order
   Order status = PAYMENT\_FAILED

## Solution: Saga Pattern

Saga manages transactions across multiple microservices using local transactions and compensating actions.

| Operation | Compensation |
| --- | --- |
| Create order | Cancel order |
| Reserve inventory | Release inventory |
| Charge payment | Refund payment |

One important distinction:

- If payment definitely failed, release inventory.
- If payment timed out, the outcome may be unknown. First check payment status using the payment transaction ID or idempotency key.
- If payment succeeded but the response was lost, don't charge again. Reconcile the existing payment.

Spring Boot implementation concept:

java

```java
try {
    paymentService.processPayment(orderId, amount);

    orderService.confirmOrder(orderId);

} catch (PaymentException ex) {

    inventoryService.releaseStock(orderId);

    orderService.cancelOrder(orderId);
}
```

In production, compensation should be durable and retryable rather than relying only on a synchronous `try-catch`.

Interview answer:

> I would implement the Saga Pattern. If payment fails after inventory reservation, I trigger a compensating transaction to release the stock and update the order status. If the payment outcome is unknown, I first verify the transaction status to avoid duplicate charges. If compensation fails, I persist it and retry asynchronously.

# 3. What happens if two customers order the last available item?

This is a very important database concurrency question.

## Scenario

Suppose available stock = 1.

Two customers simultaneously request the same product.

Available Stock = 1

Customer A

Request

Customer B

Request

Both read stock = 1

Race conditionBoth attempt to reserve the same item.

Without concurrency control, both customers might successfully purchase the same item.

This is called a Race Condition.

## Solution 1: Atomic SQL update (very useful in production)

Instead of reading stock first and then updating it, perform a conditional update in one SQL statement.

sql

```sql
UPDATE inventory
SET available_quantity = available_quantity - 1
WHERE product_id = 101
AND available_quantity >= 1;
```

Now check the number of updated rows.

- Updated rows = 1: Stock successfully reserved.
- Updated rows = 0: Out of stock.

Spring Data JPA:

java

```java
@Modifying
@Query("""
    UPDATE Inventory i
    SET i.availableQuantity =
        i.availableQuantity - :quantity
    WHERE i.productId = :productId
    AND i.availableQuantity >= :quantity
""")
int reserveStock(
    Long productId,
    int quantity
);
```

Service:

java

```java
@Transactional
public void reserveStock(
        Long productId, int quantity) {

    int updated = repository.reserveStock(
        productId, quantity
    );

    if (updated == 0) {
        throw new RuntimeException("Out of stock");
    }
}
```

The database ensures that concurrent updates cannot both consume the same available quantity.

## Solution 2: Pessimistic locking

Lock the inventory row while processing the reservation.

java

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("""
    SELECT i FROM Inventory i
    WHERE i.productId = :productId
""")
Optional<Inventory> findForUpdate(Long productId);
```

Only one transaction can hold the write lock on that row at a time.

## Solution 3: Optimistic locking

Use a version column.

java

```java
@Entity
public class Inventory {

    @Id
    private Long productId;

    private int availableQuantity;

    @Version
    private Long version;
}
```

If two transactions update the same version, one succeeds and the other gets an optimistic locking conflict.

Interview answer:

> I would use an atomic conditional SQL update to prevent overselling. The update checks available quantity and decreases stock in a single database operation. If zero rows are updated, the product is out of stock. For more complex inventory workflows, I can use pessimistic or optimistic locking.

# 4. What is the difference between Circuit Breaker and Retry?

Both are resilience patterns, but they solve different problems.

| Feature | Retry | Circuit Breaker |
| --- | --- | --- |
| Purpose | Try failed request again | Stop calling failing service |
| Behavior | Repeats request | Blocks requests temporarily |
| Best for | Temporary failures | Continuous failures |
| Risk | Can increase load | Prevents cascading failures |
| Example | Network timeout | Inventory Service is down |

## Retry example

Suppose Inventory Service temporarily fails.

- Attempt 1: Failed.
- Attempt 2: Failed.
- Attempt 3: Success.

Retry attempts to recover from temporary failures.

## Circuit Breaker example

Suppose Inventory Service is continuously failing.

CLOSED

Requests allowed

Failure threshold exceeded

OPEN

Requests blocked

Wait for configured open-state duration

HALF\_OPEN

Test a limited number of requests

SuccessReturn to CLOSED

FailureReturn to OPEN

## Resilience4j configuration

yaml

```yaml
resilience4j:
  retry:
    instances:
      inventoryService:
        maxAttempts: 3
        waitDuration: 1s

  circuitbreaker:
    instances:
      inventoryService:
        slidingWindowSize: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
```

Can we use both together?

Yes.

- Retry handles temporary failures.
- Circuit Breaker prevents repeated calls when failures become persistent.

Be careful with nested retries because they can multiply the number of downstream requests.

Interview answer:

> Retry is used to recover from temporary failures by attempting the request again. Circuit Breaker protects the system from continuous failures by temporarily blocking calls to an unhealthy service. In production, I can combine both with appropriate timeouts and limited retry attempts.

# 5. How do you implement Saga Pattern using Kafka?

There are two approaches:

1. Choreography-based Saga.
2. Orchestration-based Saga.

## A. Choreography-based Saga

Each microservice listens to events and publishes its own events.

Order Service

Publishes OrderCreated

Kafka

Inventory Service

Reserves stock

Kafka: InventoryReserved

Payment Service

Processes payment

PaymentCompleted

Order confirmed

PaymentFailed

Release stock

Example Kafka producer:

java

```java
kafkaTemplate.send(
    "order-events",
    orderId,
    new OrderCreatedEvent(orderId, productId, quantity)
);
```

Inventory consumer:

java

```java
@KafkaListener(topics = "order-events")
public void consume(OrderCreatedEvent event) {

    inventoryService.reserveStock(
        event.getProductId(),
        event.getQuantity()
    );

    kafkaTemplate.send(
        "inventory-events",
        new InventoryReservedEvent(event.getOrderId())
    );
}
```

Payment Service consumes `InventoryReserved` and processes payment.

If payment fails, it publishes `PaymentFailed`. Inventory Service consumes that event and releases the reservation.

## B. Orchestration-based Saga

A central Saga orchestrator controls the entire workflow.

For example:

text

```text
OrderSagaOrchestrator
        |
        |-- Create Order
        |
        |-- Reserve Inventory
        |
        |-- Process Payment
        |
        |-- Confirm Order
```

If payment fails:

text

```text
Payment Failed
      |
      v
Release Inventory
      |
      v
Cancel Order
```

### Which approach should you choose?

| Choreography | Orchestration |
| --- | --- |
| No central controller | Central Saga orchestrator |
| Services react to events | Orchestrator sends commands |
| Suitable for simpler workflows | Suitable for complex workflows |
| Can become difficult to trace | Easier to track workflow state |

Interview answer:

> I can implement Saga using Kafka with choreography or orchestration. In choreography, each service consumes events and publishes the next event. In orchestration, a central Saga orchestrator controls the sequence of operations and compensations. For complex e-commerce workflows, I generally prefer orchestration because the business flow and failure handling are easier to monitor.

# 6. How do you guarantee that an order event is not lost if Kafka is unavailable?

This is one of the most important questions in distributed systems.

## Scenario

1. Customer places an order.
2. Order Service saves the order in PostgreSQL.
3. Order Service tries to publish `OrderCreated` to Kafka.
4. Kafka is unavailable.

Now the order exists in the database, but the event wasn't published.

Data inconsistencyInventory Service never receives the order event.

## Solution: Transactional Outbox Pattern

Instead of saving the order and publishing directly to Kafka, save both the order and an event record in the same database transaction.

### Database tables

Orders table

| order\_id | status |
| --- | --- |
| 101 | PENDING |

Outbox table

| event\_id | aggregate\_id | event\_type | status |
| --- | --- | --- | --- |
| E101 | 101 | OrderCreated | NEW |

### Step-by-step flow

Order Service

Single Database Transaction

Save Order + Save Outbox Event

Outbox Publisher

Reads unpublished events

Kafka

Publishes OrderCreated

Inventory Service

Consumes event

### Spring Boot implementation

java

```java
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final OutboxRepository outboxRepository;

    public OrderService(
            OrderRepository orderRepository,
            OutboxRepository outboxRepository) {
        this.orderRepository = orderRepository;
        this.outboxRepository = outboxRepository;
    }

    @Transactional
    public void createOrder(Order order) {

        order.setStatus("PENDING");

        orderRepository.save(order);

        OutboxEvent event = new OutboxEvent();

        event.setAggregateId(order.getId());
        event.setEventType("OrderCreated");
        event.setPayload(
            "{\"orderId\":" + order.getId() + "}"
        );
        event.setStatus("NEW");

        outboxRepository.save(event);
    }
}
```

Notice that both database records are saved in one local transaction.

If the database transaction fails, neither record is committed.

If Kafka is unavailable, the outbox record remains available for publishing later.

### Outbox Publisher

A background process reads unpublished events and sends them to Kafka.

java

```java
@Scheduled(fixedDelay = 5000)
public void publishOutboxEvents() {

    List<OutboxEvent> events =
        outboxRepository.findByStatus("NEW");

    for (OutboxEvent event : events) {

        try {
            kafkaTemplate.send(
                "order-events",
                event.getAggregateId().toString(),
                event.getPayload()
            ).get();

            event.setStatus("PUBLISHED");

            outboxRepository.save(event);

        } catch (Exception ex) {
            // Keep event NEW.
            // Retry in the next publishing cycle.
        }
    }
}
```

This is a simplified illustration. For production, use concurrent-publisher coordination, safe row claiming (for example, `FOR UPDATE SKIP LOCKED`), bounded retries, monitoring and proper event serialization.

Important: There is a possibility that Kafka receives an event but the publisher crashes before updating the outbox status to PUBLISHED. The event may be published again.

Therefore, the consumer must be idempotent.

## Interview answer

> I would implement the Transactional Outbox Pattern. When creating an order, I save both the order record and the corresponding event in the same database transaction.
>
> A separate publisher process reads pending outbox events and publishes them to Kafka.
>
> If Kafka is unavailable, the event remains in the outbox table and will be retried when Kafka recovers.
>
> I would also implement idempotent consumers because the publisher can send duplicate events if it crashes after publishing but before updating the event status.
>
> This ensures reliable event delivery without requiring a distributed transaction between the application database and Kafka.

# Scenario: Inventory Service reserves stock successfully, but Payment Service goes down. What happens?

This is a real-world microservices problem involving Saga Pattern, distributed transactions, eventual consistency, and compensating transactions.

## 1. Understand the scenario

Suppose a customer orders a mobile phone worth ₹50,000.

We have four microservices:

- Order Service
- Inventory Service
- Payment Service
- Notification Service

The flow is:

1. Customer places order
   SuccessOrder Service creates order with `PENDING` status.
2. Inventory Service reserves stock
   SuccessOne mobile phone is reserved.
3. Payment Service processes payment
   FailedPayment Service is unavailable.
4. Compensating transaction
   Release the reserved inventory.
5. Update order status
   Set order status to `PAYMENT_FAILED` or `CANCELLED`.
6. Notify customer
   Inform the customer that payment could not be completed.

## 2. How do we implement this using Saga Pattern?

Saga is a sequence of local transactions. If one transaction fails, previously completed transactions are compensated.

| Service | Action | Result |
| --- | --- | --- |
| Order | Create order | Success |
| Inventory | Reserve stock | Success |
| Payment | Process payment | Failure |
| Inventory | Release stock | Compensation |
| Order | Cancel order | Compensation |

Important: We don't use one `@Transactional` transaction across all microservices. Each service manages its own local database transaction.

## 3. Spring Boot implementation example

Let's implement a simplified orchestration-based Saga.

### Step 1: Order Service

java

```java
@Service
public class OrderService {

    private final InventoryClient inventoryClient;
    private final PaymentClient paymentClient;
    private final OrderRepository orderRepository;

    public OrderService(
            InventoryClient inventoryClient,
            PaymentClient paymentClient,
            OrderRepository orderRepository) {

        this.inventoryClient = inventoryClient;
        this.paymentClient = paymentClient;
        this.orderRepository = orderRepository;
    }

    public String placeOrder(OrderRequest request) {

        Order order = new Order();
        order.setStatus("PENDING");

        order = orderRepository.save(order);

        boolean reserved = inventoryClient.reserveStock(
                request.getProductId(),
                request.getQuantity(),
                order.getId()
        );

        if (!reserved) {
            order.setStatus("INVENTORY_FAILED");
            orderRepository.save(order);
            return "Inventory unavailable";
        }

        try {
            paymentClient.processPayment(
                    order.getId(),
                    request.getAmount()
            );

            order.setStatus("CONFIRMED");
            orderRepository.save(order);

            return "Order confirmed";

        } catch (Exception ex) {

            inventoryClient.releaseStock(
                    request.getProductId(),
                    request.getQuantity(),
                    order.getId()
            );

            order.setStatus("PAYMENT_FAILED");
            orderRepository.save(order);

            return "Payment failed. Inventory released.";
        }
    }
}
```

This is an illustrative synchronous implementation. A production implementation should persist Saga progress, use idempotent commands, and recover from failures during compensation.

## 4. What if Inventory Service is also unavailable during compensation?

This is an important senior-level follow-up.

Suppose:

1. Inventory successfully reserves stock.
2. Payment fails.
3. Order Service tries to release inventory.
4. Inventory Service is also unavailable.

Now we have a distributed consistency problem.

Solution:

- Keep the order in `COMPENSATION_PENDING` status.
- Persist the compensation command.
- Retry releasing inventory using Kafka or a durable retry mechanism.
- Use an idempotency key so inventory isn't released twice.
- Alert operations if compensation continues failing.
- Use reconciliation jobs to identify stuck orders.

Never assume that calling the compensation API means compensation succeeded.

## 5. How would Kafka improve this architecture?

Instead of tightly coupling all services through synchronous REST calls, we can use Kafka.

Order Service

Creates PENDING order

Kafka: OrderCreated

Inventory Service

Reserves stock

Kafka: InventoryReserved

Payment Service

Processes payment

SuccessPaymentCompleted

Order CONFIRMED

FailurePaymentFailed

Release inventory

Kafka makes the workflow asynchronous, but it does not automatically guarantee successful payment or compensation.

For reliability, implement:

- Transactional Outbox Pattern.
- Idempotent consumers.
- Retry topics and Dead Letter Topics.
- Saga state persistence.
- Eventual consistency.

> In this scenario, I would implement the Saga Pattern to maintain consistency across microservices.
>
> First, Order Service creates an order with PENDING status. Inventory Service reserves the stock successfully. Then Payment Service attempts to process the payment, but it is unavailable.
>
> I would not confirm the order until payment is successful.
>
> If payment fails, I would trigger a compensating transaction to release the reserved inventory and update the order status to PAYMENT\_FAILED or CANCELLED.

>
> This approach provides eventual consistency without requiring a distributed database transaction.
